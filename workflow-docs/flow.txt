# Garbage Collection GPS Monitoring & PID Visit Tracking Portal
## Complete Project Workflow & Technical Development Specification

**Project Type:** Web-based Garbage Collection Monitoring System  
**Frontend:** React.js  
**Backend:** Node.js + Express.js  
**Database:** MySQL  
**Map Technology:** Leaflet.js + OpenStreetMap  
**GPS Integration:** Existing Vehicle GPS Tracker API  
**Deployment:** Existing Ubuntu/Linux Server

# 1. PROJECT OVERVIEW

Develop a centralized Garbage Collection GPS Monitoring Portal that enables municipal authorities to monitor garbage collection vehicles, track their movement in real time, and automatically identify which Property IDs (PIDs) have been covered by garbage collection vehicles.

The system must use the GPS trackers already installed in garbage collection vehicles. No additional hardware, RFID tags, QR codes, or physical sensors should be required.

The portal must automatically compare vehicle GPS coordinates with the geographical coordinates of registered PIDs and determine whether a vehicle has passed sufficiently close to a PID.

The system should provide:

- Live vehicle tracking on a map.
- PID-wise garbage collection visit tracking.
- Automatic PID visit detection using GPS coordinates.
- Route-wise and vehicle-wise monitoring.
- Daily collection coverage reports.
- Missed PID identification.
- Historical vehicle movement.
- Zone, ward, agency, and vehicle-level dashboards.
- Administrative management and configuration.

**Important:** GPS proximity confirms that a vehicle passed near a property. It does not independently prove that garbage was physically collected. Therefore, the system must use statuses such as "GPS Visit Detected" and "Collection Not Verified" rather than falsely claiming confirmed collection.

# 2. CORE BUSINESS OBJECTIVE

The primary objective is to answer the following questions:

1. Which garbage collection vehicles are currently running?
2. Where is each vehicle currently located?
3. Which PIDs were covered by a vehicle today?
4. Which PIDs are still not covered?
5. Which vehicle covered a particular PID?
6. At what time was a PID detected as visited?
7. Which routes have been completed?
8. Which vehicles have deviated from their assigned routes?
9. How much of the assigned area has been covered?
10. Which zones, wards, agencies, and vehicles are performing well or poorly?

# 8. AUTOMATIC PID VISIT DETECTION ENGINE

This is the core functionality of the complete portal.

The system must automatically detect whether a vehicle has passed near a registered PID using GPS coordinates.

## 8.1 Basic Logic

Every PID has a fixed latitude and longitude.

Every GPS record contains:
- Vehicle latitude
- Vehicle longitude
- GPS timestamp

Calculate the geographical distance between the GPS point and PID coordinates using the Haversine formula.

If the distance is within the configured visit radius, consider that PID as a GPS proximity match.

Example:

PID coordinates:

Latitude: 28.4082  
Longitude: 77.3178

Vehicle GPS coordinates:

Latitude: 28.4084  
Longitude: 77.3179

Distance: Approximately 24 metres.

If configured radius is 30 metres, the system can register a GPS visit candidate.

## 8.2 Configurable Detection Parameters

Create an admin configuration module.

Default starting configuration:

- PID detection radius: 30 metres.
- Minimum GPS quality: Valid coordinates and timestamp.
- Maximum acceptable GPS data age: 5 minutes.
- Minimum speed: Configurable.
- Maximum speed: Configurable.
- Consecutive GPS confirmation points: 2.
- Duplicate visit prevention: Enabled.
- Visit detection enabled: Yes.

These are initial configurable values, not universal GPS accuracy guarantees. They must be tested in actual field conditions and adjusted.

Do not permanently hardcode these values.

## 8.3 Visit Detection Algorithm

For every new valid GPS coordinate:

1. Identify the vehicle.
2. Identify its active route assignment for that date.
3. Fetch PIDs assigned to that route.
4. Find PIDs located within the configured search radius.
5. Calculate accurate distance using Haversine.
6. Validate GPS timestamp and data quality.
7. Check whether the vehicle was moving or stationary.
8. Check consecutive GPS points when available.
9. Confirm the proximity event.
10. Save the PID visit record.
11. Update the daily PID coverage status.

Use a spatial pre-filter or geographical bounding box to avoid calculating the distance against every PID in the database for every GPS point.

Use appropriate MySQL indexes and optimize queries.

## 8.4 Duplicate Detection

A PID should not be counted multiple times for the same vehicle and route assignment on the same operational day unless a separate revisit event is intentionally recorded.

Store:
- First visit time
- Last visit time
- Number of detection events
- Vehicle ID
- Route ID
- Distance from PID
- GPS record reference
- Detection status

Maintain raw GPS data separately from visit detection records.

## 8.5 Important GPS Accuracy Considerations

The system must not mark a PID visited based on an unreliable single GPS point.

Consider:
- GPS accuracy variation.
- Dense residential streets.
- Adjacent properties.
- GPS signal drift.
- Duplicate coordinates.
- Missing GPS points.
- Vehicle passing on a nearby parallel road.

If a vehicle passes close to several nearby PIDs, the system must not automatically claim that each individual property was collected.

Use the following detection classifications:

- GPS Visit Confirmed: Sufficient valid proximity evidence.
- GPS Visit Candidate: Proximity detected but confirmation conditions are incomplete.
- Not Visited: No qualifying proximity event found.
- GPS Data Unavailable: Insufficient GPS data to determine coverage.
- Unassigned PID: PID is not assigned to an active route.

Allow the administrator to configure whether consecutive GPS points, dwell time, or other evidence are required.

**Do not represent GPS proximity as proof of physical garbage collection.**

# 23. DAILY OPERATIONAL WORKFLOW

The complete system must operate as follows:

**Step 1: Master Setup**

Admin creates zones, wards, agencies, vehicles, and PIDs.

**Step 2: PID Geolocation**

All PIDs are imported with latitude and longitude. Missing coordinates are corrected using the map.

**Step 3: Route Creation**

Admin creates routes and assigns relevant PIDs.

**Step 4: Vehicle Assignment**

Vehicles and agencies are mapped to routes for a particular operational date.

**Step 5: GPS Data Collection**

Background job fetches GPS locations from the provider.

**Step 6: GPS Processing**

Backend normalizes and stores vehicle GPS coordinates.

**Step 7: PID Detection**

The detection engine checks whether vehicles pass within the configured distance of assigned PIDs.

**Step 8: Coverage Update**

Qualifying proximity events update PID daily statuses.

**Step 9: Live Monitoring**

Supervisors view vehicle positions, routes, visited PIDs, and remaining PIDs.

**Step 10: Daily Reporting**

At the end of the operational day, reports are generated automatically.

**Step 11: Historical Review**

Administrators can view previous dates, routes, vehicle activity, and PID coverage.
